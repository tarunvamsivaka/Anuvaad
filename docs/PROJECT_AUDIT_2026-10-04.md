## Findings and resolution

### Resolved in this checkout

1. **P1 — Generated code was sent to clients before AST validation.** `app/services/ai.py` streamed every provider chunk before parsing and syntax verification, and treated parse errors as a warning. It now buffers code-to-code output, rejects parse errors or validation failures, and emits chunks only after validation succeeds. AST symbol-contract extraction now runs via `asyncio.to_thread` to avoid blocking the async request loop.
2. **P1 — One history path persisted generated source as the input summary.** The sync English-to-code route passed `updated_code` as `input_text`. It now stores a length/language metadata summary and includes the receipt digest as `input_hash`.
3. **P1 — Public signing key fallback made audit receipts forgeable.** `app/core/audit.py` no longer uses a hard-coded public string when both existing secrets are absent. Receipt generation fails closed; receipt verification returns false. Production still needs a real secret configured (the existing JWT or token-encryption key can currently serve as fallback).
4. **P2 — OAuth discarded the post-login destination.** Google and GitHub flows now forward the already-sanitized `redirectTo` value into the callback's `next` parameter. The server-side callback continues to validate local paths.
5. **P2 — Share-page metadata exposed source previews to crawlers and link unfurlers.** Open Graph, Twitter, and description metadata now use generic language-pair text rather than `input_preview`.
6. **P2 — Analytics identification used email as the PostHog distinct ID.** The frontend now uses the Supabase user ID, retaining the existing consent gate.
7. **P1 — Several code-generation paths returned code without a successful syntax check.** English-to-code generation, direct code updates, and sync now require a successful Tree-sitter verification and reject validation errors. The code-to-code stale-history fallback is also checked before it can be returned. English-to-code cache hits now pass the same validation before return; invalid cached entries are evicted. The web client now parses the English-to-code endpoint's JSON response rather than feeding it to the SSE parser.

### Open findings requiring infrastructure or product follow-up

1. **P1 — Compiler checks wrote complete snippets to local temporary files. RESOLVED IN CHECKOUT.** `app/services/sandbox/compiler_runner.py` now validates Python in memory and uses Tree-sitter for other languages. It does not launch compilers or write source to temporary files. It fails closed when a parser is unavailable. This limits validation to syntax checks and can reduce coverage versus native compilers.
2. **P1 — Privacy copy contradicted saved history, shares, and provider processing. RESOLVED IN CHECKOUT.** The landing pricing surface no longer promises zero code storage; the app and static privacy pages now describe provider processing, signed-in history, explicit share links, and the limits of API-level ephemeral mode. Translation workspace runs default to skipping application history/cache; signed-in users must explicitly enable the save checkbox, and guests cannot enable it. The public whitepaper was rewritten to distinguish application behavior from provider, host, and diagnostic retention. This local behavior is unverified; live service log-retention settings still need verification.
3. **P1 — Supabase leaked-password protection is disabled.** The Supabase security advisor reported `auth_leaked_password_protection` as WARN. Enable it in Supabase Auth settings and decide how to handle existing weak passwords. [Supabase password security guidance](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
4. **P1 — Render production database and Redis connectivity are failing.** A live log sample from October 4 shows Supabase pooler `tenant/user not found` errors on subscription reads and Redis connection timeouts. The service falls back to in-memory rate-limit/cache counters when Redis fails, and subscription errors are swallowed by repository code, so endpoints may respond 200 while showing default/free subscription data. The service environment values are not exposed by the connector; correct `DATABASE_URL`/`DATABASE_POOL_URL` host, username, password, and `REDIS_URL` in Render, then recheck logs and a live health/functional endpoint. Do not paste credentials into chat.
5. **P2 — Render's live configuration differs from `render.yaml`. PARTIALLY RESOLVED IN CHECKOUT.** The Blueprint specifies the live free plan and `uvicorn main:app` entry point, and omits the unsupported free-plan pre-deploy step. Live inspection shows one free Python service on `master` in Oregon with no health-check path configured; runtime configuration could not be compared to the Blueprint because the Render API does not return environment values. Render documents pre-deploy commands as available for paid web services, so production schema changes need a separately owned migration procedure while the API remains on the free plan. [Render pre-deploy documentation](https://render.com/docs/deploys).
5. **P2 — Free quota differed between marketing and backend/deployment config. RESOLVED IN CHECKOUT.** A public API endpoint now publishes the configured normal-mode guest/free daily limits from the same `compute_quota_policy()` function used for enforcement. Landing, signup, terms, quota prompt, and billing surfaces read those values at runtime. The signed-in `/usage` route now uses the same policy including the active protection mode; the superseded quota constants were removed. No quota values are hard-coded into active UI copy.
6. **P2 — Product and migration surfaces are broader than a focused consumer MVP. PARTIALLY RESOLVED IN CHECKOUT.** Structured metadata, landing headline, onboarding, workspace descriptions, and demo copy no longer claim universal/“35+” support, instant results, or perfect code. The changelog no longer presents unverified latency/accuracy numbers or describes audit digests as zero-data-retention proof. The landing page labels its language list as examples and notes parser coverage varies. The translation toolbar now displays parser/syntax-check availability for the selected language from the backend registry; this is an availability signal, not evidence of semantic correctness or end-to-end translation quality. Teams, PR review, enterprise/VPC/compliance positioning, and end-to-end quality coverage still need validation before launch; keep capability labels clearly scoped and narrow the launch promise to routes and language pairs validated end to end.
7. **P2 — Database migration ownership and historical drift remain unresolved. PARTIALLY ADDRESSED IN CHECKOUT.** Production `public.alembic_version` is `014_fix_supabase_security_and_indexes`, matching the latest local Alembic revision. Supabase separately reports ten migration-ledger entries, whose source SQL is absent from the repository. A forward policy now assigns application PostgreSQL DDL to Alembic, and CI checks for exactly one Alembic head. The Supabase ledger must still be reconciled against Alembic, especially the September 30 security/performance change; the existing CI migration test covers only revisions 006→007, not the full upgrade chain. See [database migration policy](DATABASE_MIGRATION_POLICY.md).
8. **P3 — Supabase advisor reports 35 unused indexes.** This is informational, not proof that the indexes are unnecessary: the project may be new or the workload sparse. Review query plans and production usage over a representative period before dropping anything. Do not delete indexes based on the linter alone.
9. **P3 — Render had no useful request/latency/CPU time series in the returned metrics snapshot. PARTIALLY ADDRESSED IN CHECKOUT.** The authenticated metrics snapshot and Prometheus endpoint now expose a per-process rolling p95 over the latest 100 requests, alongside existing request/error/model/memory metrics. The connected Render snapshot still had no useful time series, and no external dashboard/alerts were configured here. Memory usage was approximately 186 MB at the sampled point. Confirm collection and add alerts for error rate, latency, memory, and provider failure before a consumer launch.
10. **P3 — `gitleaks` could not execute in this Windows environment.** `.env` is ignored and untracked, but the repository still needs a successful CI or maintainer secret scan before a public release. Keep credentials out of logs and rotate any key found in Git history.
11. **P2 — Client roles had broad SQL table privileges despite effective RLS. RESOLVED IN CHECKOUT; NOT YET APPLIED.** Live inspection found RLS enabled on all 23 public tables and 35 policies, with no unconditional `true` policy for `anon` or `public`. `anon` and `authenticated` each held all seven table privileges on every table and on the public stats view; the `postgres` default ACL also grants all table and sequence privileges for future objects. The browser-facing Data API use in the repository is the landing-lead insert; other database paths are backend-owned or use the server-side service key. Alembic revision `015_revoke_public_table_grants` revokes client table/sequence grants, removes broad default grants for the PostgreSQL migration owner, and regrants `anon` column-level INSERT only on `landing_leads.email` and `landing_leads.source`. The full-chain CI test asserts the active grants. Production remains on revision 014 until this change passes CI and follows the documented release procedure.
